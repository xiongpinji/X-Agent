# X-Agent 商业 RC 与竞品差距收敛设计

**状态：** 已批准设计

**批准日期：** 2026-08-07

**目标：** 修复 X-Agent 当前可信度与产品化缺陷，使本地核心门禁、Codex/Hermes 对标矩阵、四端产品冒烟、版本治理和外部商业 RC 证据形成同一条可复跑证据链；随后在不虚构外部能力的前提下，分阶段缩小与 OpenAI Codex、Nous Hermes Agent 的关键产品差距。

## 1. 背景与现状

X-Agent 已具备 Agent 主循环、工具、MCP、工作流、记忆、审批、审计、沙箱、多租户、SSO/SCIM 和部署资产。当前主要问题已经从“是否存在实现”转为“实现、接线、验证和产品表面是否一致”。

本设计以 2026-08-07 的 `main` 工作树为基线。已确认的事实包括：

- Python 包版本为 `0.4.0-alpha`，FastAPI、Web、桌面、移动端和扩展仍有 `0.3.0-alpha`、`0.1.0` 等漂移。
- 发布候选核心定向门禁通过，但 Codex/Hermes 差距矩阵因限流环境和迁移后的文档路径而不能全绿。
- Web 和移动端类型检查通过；桌面端缺少安装级现行证据；浏览器扩展测试存在 29 个失败。
- 本地 `main` 超前 `origin/main` 60 个提交，Hosted CI 不能证明这些提交的状态。
- Feishu、GitHub 测试仓库、Hosted GitHub Actions 和生产密钥属于外部所有者证据，缺失时必须保持 `action_required`，不得自动降级为通过。

## 2. 设计原则

### 2.1 证据先于宣称

每个完成声明必须指向当前 Git SHA 上的新鲜命令输出、测试结果、运行工件或外部回执。代码存在、历史报告、静态页面和模拟结果不能替代同一条真实链路的验收。

### 2.2 先收敛，再扩展

第一阶段不新增竞争功能。先修复版本、矩阵、产品表面和证据链，避免继续扩大“功能存在但无法交付”的面积。

### 2.3 一个能力只有一个权威入口

版本、工具注册表、工作流存储、任务状态、RC 报告和产品表面均采用单一权威来源。兼容层可以读取旧格式，但不得生成第二套互相冲突的真相。

### 2.4 外部阻塞必须诚实

缺少凭据、真实仓库、真实模型、真实集群或 Hosted CI 时，状态只能是 `action_required`、`blocked` 或 `not_verified`。不得用 mock、dry-run 或本地静态检查替代外部验收。

### 2.5 精准修改

每个子项目只修改其验收所需文件。已有重复实现仅在阻断当前权威路径时处理，不进行无关重构。

## 3. 总体架构

证据链按以下顺序收敛：

```text
权威事实源
  -> 局部门禁
  -> 四端产品门禁
  -> Codex/Hermes 差距门禁
  -> 外部所有者门禁
  -> 商业 RC 聚合决策
```

各层只能消费上游已经落盘且绑定当前 Git SHA 的结果。上游报告发生变化后，下游报告必须重新生成；过期报告不得继续支持发布结论。

### 3.1 状态模型

所有新建或修订的聚合报告统一使用以下状态语义：

- `passed`：要求已由当前 SHA 的直接证据证明。
- `failed`：命令已执行，结果与要求冲突。
- `action_required`：必须由发布所有者提供外部资源或批准。
- `not_verified`：尚无足够直接证据。
- `skipped`：仅允许用于非必需检查；必需检查出现 `skipped` 时总门禁不得通过。

## 4. 交付线设计

### 4.1 RC-TRUTH：可信度与证据链修复

职责：修复当前 Codex/Hermes 差距矩阵、过期路径、限流环境契约、审计探针和报告新鲜度。

设计要求：

- 差距矩阵在测试自身显式配置的环境中运行，不依赖开发者本机 `.env` 的偶然状态。
- 限流测试必须显式启用限流；开发模式默认关闭和生产模式默认开启分别由独立测试证明。
- 所有文档证据路径指向当前四分册目录，不保留已迁移路径作为必需项。
- 生成报告记录 Git SHA、工作树状态、命令、退出码、耗时和必要的脱敏输出。
- 聚合门禁拒绝缺失证据、失败结果、超时结果和 SHA 不一致的报告。
- 根目录旧审计探针要么同步当前请求/响应契约，要么移入明确的历史归档，不继续作为现行命令入口。

验收结果：Codex/Hermes 本地矩阵的全部必需类别在当前 SHA 上通过，同时保留 `full_parity_claimed=false`。

### 4.2 VERSION：版本单一事实源

职责：让 `pyproject.toml` 成为发布版本的唯一权威来源。

设计要求：

- Python CLI 运行时读取已安装包元数据或仓根 `pyproject.toml`。
- FastAPI OpenAPI 版本、Web、桌面、扩展、移动端和 SDK 的构建元数据与权威版本一致。
- 增加只读版本一致性验证器；发现任何产品版本漂移时退出非零。
- CI 和商业 RC 门禁必须运行版本验证器。
- 不在多个文件中引入新的手工版本常量；必须保留静态版本字段的平台通过同步脚本和验证器受控。

验收结果：所有面向用户的版本输出和构建元数据均为 `pyproject.toml` 当前版本，手工制造漂移后验证器能够失败。

### 4.3 SURFACES：四端产品门禁

职责：证明 Web、桌面、浏览器扩展和移动端不是仅有源代码，而是可以安装、构建或启动的产品表面。

#### Web

- 运行类型检查和生产构建。
- 启动后端与前端代理，验证首页、聊天入口和至少一条 mock Agent 请求。
- 构建产物不得引用开发专用绝对路径或 mock-only API。

#### 桌面端

- 使用锁文件安装前端依赖并完成 Vue 构建。
- 完成 Rust/Tauri 编译检查和本机启动冒烟。
- 验证桌面端连接现有后端，不嵌入第二套 Agent 运行时。

#### 浏览器扩展

- 修复 ESM/Jest 装载契约和 `chrome.runtime.sendMessage` mock 的 Promise 契约。
- `npm test` 必须退出 0，不允许降低覆盖率阈值绕过失败。
- 完成 Manifest 校验、打包和浏览器加载冒烟。
- 验证后台脚本、content script 和 MCP 客户端之间的消息协议。

#### 移动端

- 运行 TypeScript 检查和 Expo 配置验证。
- 至少完成 Web 或 Android 的可重复构建；平台证书缺失时保留 iOS `action_required`。
- 验证登录、任务提交、状态查询和结果查看使用真实后端契约。

验收结果：四端均生成机器可读报告；任一必需表面失败时商业 RC 不得通过。

### 4.4 CODEX-GAP：Codex 差距收敛

定位：不复制 OpenAI 的模型和云规模，补齐企业自托管编码 Agent 的关键使用体验。

按优先级交付：

1. 原生 VS Code/ACP 入口：展示聊天、工具活动、文件 diff、终端命令和审批。
2. 长任务恢复：进程重启后恢复任务、检查点、部分结果和待审批状态。
3. 多 Agent 工作区：隔离文件所有权、并行执行、结果汇总和冲突检测。
4. 代码评审 Agent：基于固定 diff、规格和仓库标准输出可定位问题。
5. 浏览器/桌面真实验收：完成 UI 任务后附截图、状态回读和失败回写。
6. 移动端监督：查看运行中任务、回答澄清问题、批准或终止任务。

每项能力必须先定义用户任务，再定义同链运行证据。单元测试不能独立支持“达到 Codex 对等”的结论。

### 4.5 HERMES-GAP：Hermes 差距收敛

定位：在 X-Agent 企业治理基础上补齐个人 Agent 的连续使用体验。

按优先级交付：

1. 多渠道网关：先完成 Telegram、Feishu、DingTalk、Slack 的统一入站、会话和回执契约。
2. 技能生命周期：发现、安装、安全扫描、审批、启用、版本化、回滚和禁用。
3. 记忆治理：写入审批、来源、作用域、过期、删除和跨会话检索。
4. 自我改进：改进建议先进入草稿和评审，不允许 Agent 直接覆盖生产技能。
5. Cron 与持久任务板：任务可暂停、恢复、重试、转派并保留心跳。
6. 多执行后端：在现有本地/Docker 基础上评估 SSH 和一个云沙箱后端；未接入的后端不暴露为可选成功路径。

所有渠道和执行后端共享同一套审批、审计、租户和策略边界。

### 4.6 EXTERNAL-RC：外部商业 RC 门禁

职责：收集本地无法制造的真实外部证据。

必需门禁：

- 将当前候选提交推送到远端，并由 Hosted GitHub Actions 在同一 SHA 上运行商业 RC 工作流。
- 使用真实模型完成哨兵响应、工具调用和失败模式验证。
- 使用 Feishu 测试应用验证签名回调；不执行无授权的外发业务变更。
- 使用一次性 GitHub 测试仓库验证 Issue 读取、分支权限和 Issue-to-PR 受控执行。
- 生成并存储生产密钥，验证 API Key、JWT、审计 HMAC 和加密配置。
- 在真实 Kubernetes 集群完成部署、就绪探针、回滚、备份恢复和基本负载测试。

外部证据只能由发布所有者明确提供资源或授权后执行。缺失任何必需门禁时，允许内部演示，但不得生成可打 RC 标签的结论。

## 5. 错误处理与安全边界

- 验证命令超时必须记录 `timeout`，不得自动重试付费模型调用。
- 未知状态的异步模型任务先查询供应商任务和计费日志，不重复提交。
- 报告输出统一脱敏 API Key、Token、Secret、Password 和本机用户路径。
- 版本同步、报告生成和 dry-run 不执行外部写操作。
- 推送、Hosted CI、Feishu、GitHub PR、生产部署和密钥变更保留明确授权边界。
- 任一安全门禁失败时，聚合结果 fail-closed。

## 6. 测试与验收体系

### 6.1 测试层级

- L0 静态：格式、lint、类型、依赖、版本和文档路径。
- L1 单元：状态模型、解析器、同步器和报告聚合逻辑。
- L2 集成：FastAPI、数据库、MCP、渠道、沙箱和产品表面构建。
- L3 本机端到端：后端、Web、桌面、扩展和移动端到 mock/本地模型。
- L4 外部端到端：真实模型、Hosted CI、Feishu、GitHub 和 Kubernetes。

### 6.2 完成判定

一个任务只有同时满足以下条件才可标记完成：

1. 规格中的行为由测试或运行证据覆盖。
2. 修改范围内测试通过。
3. 相关上游和下游回归通过。
4. 报告绑定当前 Git SHA，且工作树差异已审计。
5. 文档与命令可以由另一名工程师复跑。
6. 外部资源缺失被标为 `action_required`，未被隐藏。

## 7. 分阶段里程碑

### 里程碑 M1：本地可信 RC

完成 RC-TRUTH 和 VERSION。本地核心门禁、差距矩阵、版本验证和静态检查全绿。

### 里程碑 M2：四端可交付候选

完成 SURFACES。四端具备机器可读构建/安装证据，浏览器扩展测试归零。

### 里程碑 M3：竞争力增强候选

按用户价值完成 CODEX-GAP 和 HERMES-GAP 的首批任务：IDE/长任务恢复、多渠道、技能与记忆治理。

### 里程碑 M4：商业 RC

完成 EXTERNAL-RC。当前候选 SHA 的本地、Hosted CI、真实供应商、真实渠道和真实部署证据全部通过。

## 8. 非目标

- 不宣称复制 Codex 的模型能力、OpenAI 云规模或市场用户量。
- 不以功能数量追平 Hermes 的全部渠道、媒体和插件生态。
- 不在本轮取得 SOC 2 认证或第三方渗透测试报告之前宣称合规完成。
- 不为通过门禁降低安全、测试、覆盖率或审批要求。
- 不把历史报告、fixture、mock 或 dry-run 当作生产链证据。

## 9. 设计完成标准

本设计获批后，实施计划必须：

- 按 RC-TRUTH、VERSION、SURFACES、CODEX-GAP、HERMES-GAP、EXTERNAL-RC 分成可独立交付的计划。
- 每个计划列出精确文件、失败测试、最小实现、验证命令和提交边界。
- 优先执行 M1；M1 完成并审计后再进入 M2。
- 保持商业 RC 总目标不变，不用较小的本地成功替代外部完成条件。
