## 执行摘要

X-Agent 灾难恢复计划（DRP）确保在发生重大故障时，系统能够快速恢复并最小化数据丢失。本计划涵盖：

- **多区域部署**：主区域 + 备用区域（热备）
- **实时数据同步**：主从复制 + 双向同步
- **自动故障转移**：DNS切换 + 流量转移
- **恢复验证**：数据完整性检查 + 功能测试
- **定期演练**：每季度一次完整演练

### 关键指标

| 指标 | 目标 | 当前 |
|------|------|------|
| RTO（恢复时间目标） | <1小时 | 45分钟 |
| RPO（恢复点目标） | <15分钟 | 5分钟 |
| 数据丢失率 | <0.1% | 0% |
| 服务可用性 | 99.99% | 99.95% |
| 故障转移自动化 | >95% | 98% |
| 演练成功率 | 100% | 100% |

## RTO/RPO目标

### 恢复时间目标（RTO）

**定义**：从故障发生到系统完全恢复的时间

| 故障类型 | RTO目标 | 实现方式 |
|---------|--------|--------|
| 应用服务故障 | 5分钟 | 自动重启 + 负载均衡转移 |
| 单个数据库节点故障 | 15分钟 | 主从切换 + 自动转移 |
| 整个数据中心故障 | 45分钟 | 跨区域转移 + DNS切换 |
| 全局故障 | 1小时 | 手动干预 + 完整恢复 |

### 恢复点目标（RPO）

**定义**：可接受的最大数据丢失量

| 数据类型 | RPO目标 | 实现方式 |
|---------|--------|--------|
| 关键业务数据 | 5分钟 | 实时复制 + WAL日志 |
| 用户会话数据 | 15分钟 | Redis主从复制 |
| 向量数据库 | 10分钟 | Qdrant快照 + 增量同步 |
| 图数据库 | 10分钟 | Neo4j备份 + 增量同步 |

## 故障检测与转移

### 1. 健康检查机制

#### 应用层健康检查

```yaml
检查间隔: 10秒
超时时间: 5秒
失败阈值: 3次连续失败
恢复阈值: 2次连续成功

检查项:
  - HTTP GET /health
  - 数据库连接
  - Redis连接
  - 消息队列连接
  - 外部API连接
```

#### 数据库健康检查

```yaml
PostgreSQL:
  - 连接测试
  - 复制延迟监控 (目标: <1秒)
  - 磁盘空间监控 (告警: >80%)
  - 连接数监控 (告警: >80%)

Redis:
  - PING命令
  - 内存使用监控
  - 复制延迟监控
  - 持久化状态检查

Qdrant:
  - HTTP健康检查
  - 集合状态检查
  - 磁盘空间监控

Neo4j:
  - 连接测试
  - 事务日志检查
  - 集群状态检查
```

### 2. 自动故障转移

#### DNS转移

```bash
# 主区域故障时的DNS切换流程
1. 检测主区域所有应用实例不可用
2. 更新Route53记录指向备用区域
3. 等待DNS传播 (TTL: 60秒)
4. 验证流量已转移到备用区域
5. 记录转移事件到审计日志
```

#### 流量转移

```bash
# 负载均衡器转移流程
1. 检测后端实例健康状态
2. 自动从负载均衡器移除故障实例
3. 将流量转移到健康实例
4. 如果所有实例故障，转移到备用区域
5. 触发告警通知运维团队
```

#### 数据库转移

```bash
# PostgreSQL主从切换
1. 检测主库不可用
2. 提升从库为新主库
3. 更新应用连接字符串
4. 验证写入操作正常
5. 启动新的从库

# Redis转移
1. 检测主库不可用
2. 提升从库为新主库
3. 更新应用连接配置
4. 验证缓存操作正常
```

### 3. 手动转移流程

当自动转移失败时，运维团队可以手动执行转移：

```bash
# 1. 评估故障
./scripts/dr/assess-failure.sh

# 2. 执行手动转移
./scripts/failover.sh --manual --region us-west --force

# 3. 验证转移
./scripts/dr/verify-failover.sh

# 4. 通知相关方
./scripts/dr/notify-stakeholders.sh
```

```bash
3. 重启故障节点
```


```bash

2. 停止所有写入操作
```

## 灾难恢复手册

### 1. 故障分类与响应

#### 网络故障

**症状**：
- 应用无法连接到数据库
- 跨区域通信中断
- DNS解析失败

**响应步骤**：
```bash
1. 检查网络连接: ping <database-host>
2. 检查DNS: nslookup <service-name>
3. 检查防火墙规则: aws ec2 describe-security-groups
4. 检查路由表: aws ec2 describe-route-tables
5. 如果本地网络故障，转移到备用区域
6. 如果跨区域网络故障，启用备用网络链路
```

#### 应用服务故障

**症状**：
- API返回5xx错误
- 应用进程崩溃
- 内存溢出

**响应步骤**：
```bash
1. 检查应用日志: docker logs xagent-api
2. 检查资源使用: docker stats xagent-api
3. 重启应用: docker restart xagent-api
4. 如果重启失败，转移到备用实例
5. 分析崩溃原因
6. 部署修复版本
```

#### 数据库故障

**症状**：
- 数据库连接超时
- 查询响应缓慢
- 复制延迟过大

**响应步骤**：
```bash
1. 检查数据库状态: psql -c "SELECT version();"
2. 检查复制状态: psql -c "SELECT * FROM pg_stat_replication;"
3. 检查磁盘空间: df -h
4. 检查连接数: psql -c "SELECT count(*) FROM pg_stat_activity;"
5. 如果主库故障，执行主从切换
6. 如果从库故障，重建从库
```

#### 数据中心故障

**症状**：
- 所有服务不可用
- 无法连接到任何资源
- 网络完全中断

**响应步骤**：
```bash
1. 确认主区域完全不可用
2. 执行跨区域转移: ./scripts/failover.sh --auto
3. 验证备用区域服务正常
4. 更新DNS指向备用区域
5. 通知所有利益相关者
6. 启动故障根因分析
7. 制定恢复计划
```

### 2. 应急响应流程

#### 分级响应

**P1 - 严重故障** (RTO: 15分钟)
- 所有用户无法访问系统
- 数据丢失风险
- 业务完全中断

响应：
- 立即激活灾难恢复团队
- 执行自动故障转移
- 每5分钟更新状态
- CEO通知

**P2 - 重大故障** (RTO: 1小时)
- 部分用户无法访问
- 功能受限
- 业务部分中断

响应：
- 激活运维团队
- 执行故障转移
- 每15分钟更新状态
- 管理层通知

**P3 - 中等故障** (RTO: 4小时)
- 特定功能不可用
- 性能下降
- 业务轻微影响

响应：
- 通知相关团队
- 分析根因
- 每小时更新状态

**P4 - 轻微故障** (RTO: 24小时)
- 非关键功能受影响
- 用户体验下降
- 业务无影响

响应：
- 记录问题
- 计划修复
- 定期跟进

### 1. 关键指标监控

```yaml
应用层:
  - 请求延迟 (p50, p95, p99)
  - 错误率
  - 吞吐量
  - 活跃连接数

数据库层:
  - 查询延迟
  - 复制延迟
  - 磁盘使用率
  - 连接数
  - 事务数

  - CPU使用率
  - 内存使用率
  - 磁盘I/O
  - 网络带宽
  - 网络延迟

业务指标:
  - 用户活跃度
  - 交易成功率
  - 数据一致性
```

### 2. 告警规则

```yaml
严重告警 (P1):
  - 应用不可用 (连续3次健康检查失败)
  - 数据库不可用
  - 数据中心故障
  - 数据丢失检测

重要告警 (P2):
  - 复制延迟 >5分钟
  - 磁盘使用率 >90%
  - 连接数 >90%
  - 错误率 >1%

普通告警 (P3):
  - 响应时间 >1秒
  - CPU使用率 >80%
  - 内存使用率 >85%
  - 磁盘使用率 >80%
```

### 3. 告警通知

```yaml
通知渠道:
  - 邮件 (所有告警)
  - Slack (P1/P2告警)
  - 短信 (P1告警)
  - 电话 (P1告警 + 无响应)

通知延迟:
  - P1: <1分钟
  - P2: <5分钟
  - P3: <15分钟
```
